# 2026-09-10: repeated 921600 IRQ tests

**921600 is not qualified on either current end-to-end link.** Thirty-five
trials reproduced burst losses, including occasional USART1/CH340 loss.
Earlier individual passes remain valid observations, not a reliability claim.
No 3-Mbaud or DMA tests, driver changes, probe-mode changes or wiring changes
were performed in this follow-up.

The later [IRQ flight-recorder session](hardware-20260910-irq-trace.md) adds
sampled RAM diagnostics and captures hardware ORE with a significant observer
effect. It leaves a 921600 diagnostic image installed, per the owner's new
workflow; this report's 115200 restoration is historical, not a standing rule.

## Fixed setup and method

Use the corrected wiring from the [IRQ report](hardware-20260910-irq.md).
The MCU image, Zephyr/HAL/SDK and driver are unchanged from that report:
921600 binary SHA-256
`1b1aab183e66439f9bf18fd03c01c418617c73ffbdcab0fbb79de94d2c11662c`.
WCH-LinkE 2.19 and onboard CH340E remain attached to the same Linux host.

The new `tests/host/uart_irq_repeat.py` performs five reset-isolated trials
per case, at 921600 8N1, without flow control. Each selected port attempts
128 request/echo blocks, with port/sequence identifiers and deterministic
trial-specific pseudorandom bytes. Every byte must match; missing data gets
a one-second deadline. Each port stops at its first failed block; its peer
may finish independently. Dual means both workers start together, not that
both remain active after one fails. This is not continuous line-rate traffic.

Old serial input is drained before reset; no post-reset data is discarded.
Every trial requires the exact port-specific boot banner, CFGR0 `003c000a`
and BRR `009c`. After all workers stop, a debugger-readable snapshot records
counts, error mask, queue overflow and failure latch. No debug traffic occurs
during payload tests. A new reset precedes every next trial.

## Results

| Active ports | Bytes/block | Passed / trials | Failed / trials |
| --- | ---: | ---: | ---: |
| USART1 | 512 | 4 / 5 | 1 / 5 |
| USART2 | 32 | 5 / 5 | 0 / 5 |
| USART2 | 64 | 0 / 5 | 5 / 5 |
| USART2 | 256 | 0 / 5 | 5 / 5 |
| USART2 | 512 | 0 / 5 | 5 / 5 |
| Both | 32 | 5 / 5 | 0 / 5 |
| Both | 512 | 0 / 5 | 5 / 5 |

Total: **14 PASS, 21 FAIL, zero boot-banner failures**. Passing 32-byte
trials transferred 4096 bytes per port per direction; passing 512-byte trials
transferred 65,536. Failed trials stopped early, so do not count their intended
128 blocks as completed coverage.

- USART2 often lost exactly 64 return bytes, sometimes a prefix or an entire
  64-byte response; other failures lost smaller spans. The five USART2-only
  512-byte trials lost 64, 10, 5, 64 and 4 bytes respectively.
- USART1-only trial 1 (zero-based) lost 11 bytes in block 3: host sent 2048
  total, received 2037; MCU RX 2048 / TX 2110 including the 62-byte banner.
  USART1 also lost 10 bytes in dual trial 3; its peer had already stopped.
- In most failures the MCU's RX equaled host writes and TX equaled RX + 62.
  **Exceptions:** dual 512-byte trials 1 and 4 sent 1536 bytes to USART2 but
  its RX counted 1535 and TX 1597. The host received 1471 and 1535 respectively.
  Consequently a return-path-only explanation does not cover every failure.
- All snapshots had zero error mask, queue overflow and failure latch. These
  software snapshots do not prove that no physical UART error occurred between
  status checks, nor that every byte fed to DATAR reached the wire correctly.

## Interpretation and next gate

The failure is reproducible and strongly dependent on burst size in this
sample. Neither WCH-Link firmware nor the MCU UART driver is established as
the root cause. Do not ignore USART1 failures or the two short MCU RX counts
to claim a bridge-only defect. The next useful discriminator is independent
capture of both TX/RX wires, plus an isolated bridge test, before changing
driver behavior. Small paced transfers passing do not qualify burst traffic.

Read-only USB descriptor inspection showed WCH-Link CDC data IN/OUT maximum
packets of 64 bytes and CH340 bulk IN/OUT maximum packets of 32 bytes. The
repeated 64-byte losses and USART1 first differences at offsets 160/480
(multiples of 32) are consistent with a packet/buffering boundary problem,
but are not proof. Signal integrity, clock mismatch and ISR races remain
possible. MCU-side error counters cannot report the bridge receiver's errors.

The board is restored to the dual IRQ 115200 baseline after this campaign.
Its final dual test passed 66,049 bytes per port per direction, with matching
MCU counters and no latched errors/overflow/failure. The target was reset after
the diagnostic snapshot. No 3-Mbaud image was flashed. Preserve all failed
trials alongside passes.

## Reproduction and logs

From Ragtime, with the matching 921600 image already flashed and exactly one
intended WCH-Link attached:

```sh
.venv/bin/python ../zephyr-wch-drivers/tests/host/uart_irq_repeat.py \
  --mode 2 --size 512 --trials 5 --blocks 128 \
  --uart2 /dev/serial/by-id/<WCH-Link-CDC> \
  --diag-address 0x20000a38 --reset-tool "$PWD/build/wch-tools/bin/wlink"
```

Resolve `wch_irq_diag` from the matching ELF; the address is not a stable ABI.
Use `--mode 1` with `--uart1`, or `--mode dual` with both explicit paths.
Use sizes 32/64/128/256/512; this campaign did not run the 128-byte variant.
The script emits JSON per trial with full failing payloads and diagnostic
counts, exits nonzero for any failed trial, and never flashes or changes
protection/power/mode. It resets after final diagnostic access.

Local raw logs: `build/test-wch-irq-921600/repeat-uart2-512.jsonl` and
`repeat-matrix.jsonl`. Host helper validation: five simulated echo sizes and
one corrupt-payload detection case passed; these are not extra hardware trials.
