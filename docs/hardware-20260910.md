# 2026-09-10: first CH32V203F8U hardware session

## Target and scope

CH32V203F8U development board matching the supplied QFN20 schematic; board
revision/marking photograph has not been recorded. Probe reports chip ID
`0x203d0500`, matching WCH's F8U ID definition. WCH-LinkE firmware 2.19,
RISC-V mode, low (400 kHz) debug connection. SDI uses PA13/PA14 and common GND;
the board is separately powered through its Type-C connector.

Type-C connects to **CH340**, not native USBFS. The supplied schematic connects
MCU PA9/TX1 to CH340 RXD through R2 and CH340 TXD to PA10/RX1 through R3.
No UART loopback jumpers were used. Exact probe serial/MCU UID stay in local
logs, not this public report. No original firmware backup was requested.

## Initial failure and board fix

The first polling image wrote/read back correctly but serial output was absent
or corrupt. After debug operations, RCC CFGR0 was `0x0034040a` (PLL x15),
while UART BRR was `0x04e2` for a configured 144 MHz/115200 baud. Device/host
elapsed-time ratios were approximately 0.831 and 0.841, consistent with a
120/144 clock mismatch; they are not calibrated oscillator measurements.

The Gello early hook originally only bypassed HSI /2. The RCC driver disables
PLL without first switching SYSCLK away from it; a debugger/reset path can
leave PLL selected, preventing its multiplier from being changed. Gello now
enables HSI, switches SYSCLK to HSI and waits for the switch, stops PLL and
normalizes AHB/APB dividers before normal RCC initialization and HSI bypass.
No Zephyr/HAL checkout or general clock driver was patched.

The resulting firmware reports its own boot snapshot over UART:
`CFGR0=0x003c000a`, `EXTEN=0x00000a50`, `BRR=0x000004e2`. This confirms x18
configuration before later debug observations. Do not infer untouched runtime
clock state from intrusive debugger commands: finish such checks with a reset
and recheck the boot snapshot/heartbeat before timing tests.
